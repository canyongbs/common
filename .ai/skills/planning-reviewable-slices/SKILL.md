# Planning Reviewable Slices

A **reviewable slice** is one self-contained pull request a reviewer can fully understand in one sitting. This skill covers deciding whether a ticket needs more than one, and planning them. The reasoning behind every rule here is in [Reviewable Slices](https://github.com/canyongbs/common/blob/main/docs/explanations/reviewable-slices.md).

## 1. Decide whether to slice

**One pull request is the default.** Most tickets do not need slicing. Plan slices when **any** of these is true:

- Your honest estimate is over about **500 readable lines** (section 2), or more than about **15 files**.
- You need "and" to describe the work in one sentence.
- The feature has more than one product-visible behaviour (two kinds of email, a setting plus the thing it controls, import plus export).
- It needs a migration, the code that uses it, and a user interface, and they will not fit together within the budget.
- It mixes a refactor or cleanup with new behaviour.
- You would not want to review it yourself in one sitting.

**Decide up front where you can.** It is far cheaper to plan slices before writing code than to split a finished branch.

**Re-check while you work.** If work in progress passes the budget, or one of the signals appears, **stop**: plan the remaining slices, then split what you have into slices before writing more. As an agent, tell the user the work has outgrown one pull request and propose a plan instead of continuing.

## 2. The size budget

Count **readable lines**: additions plus deletions in files a reviewer must read.

| Readable lines | Verdict                                                                                       |
| -------------- | --------------------------------------------------------------------------------------------- |
| Up to 500      | 🟢 **Target.**                                                                                |
| 500 to 1,000   | 🟡 **Sometimes acceptable.** Fine if it is still one concept; ask whether a split is clearer. |
| 1,000 to 1,500 | 🟠 **Large.** Heavily discouraged. The description must say why it is not split.              |
| Over 1,500     | 🔴 **Too large.** Needs an explanation and serious consideration of splitting.                |

- **Counts:** application code, tests, configuration that changes behaviour, Blade and Livewire templates, migrations, documentation, cleanup task files.
- **Does not count:** lockfiles, generated or compiled files, snapshots, baselines, images, pure renames, and the copyright header blocks our tooling adds. A deleted file counts as one line.
- **Files matter too.** More than about 15 files usually means more than one idea.
- **No change is too small.** There is no minimum size and no limit on how many slices a stack has.
- **Mechanical changes are the exception.** A framework upgrade or a change generated by a tool you trust completely may be large; keep it in its own pull request with no hand-written changes, and say it is tool-generated.

## 3. The five review-readiness tests

Every slice must pass all five:

1. **One idea.** The title needs no "and". If it does, it is two slices.
2. **Self-explanatory.** A reviewer with no context understands what it does and why from the description and the diff. Nothing essential lives only in the author's head or a later pull request.
3. **Complete for its idea.** It includes its own tests, and a **real use** of every new model, service, job or method it adds. Never add code with "this will be used in a later pull request".
4. **Safe to land.** After it merges, the application still works for users and developers. Migrations are tolerated by the code already deployed (see the `zero-downtime` guideline), nothing unfinished is reachable by a customer (it is unwired, or gated behind an inactive feature flag), and nothing customers already use changes until its replacement is switched on (see `hiding-unfinished-work`).
5. **Sized for one sitting.** Within the budget in section 2.

## 4. Slice by concept, not by layer

A **concept** is something the product does, carried through all its layers: migration, models, service or action, job, mail or notification, policy, Filament surface (gated or unwired) and tests. "The pre-meeting reminder email", "a per-tenant setting that enables a workflow" and "a CSV export of a resource" are concepts. "The models", "the jobs" and "the Filament resources" are layers.

Plan with **Google's grid**: concepts across the top, layers down the side, each cell a candidate slice.

| Layer                                  | Shared               | Concept A  | Concept B  |
| -------------------------------------- | -------------------- | ---------- | ---------- |
| Keystone (makes it customer-available) | activation (last)    |            |            |
| User interface (gated or unwired)      |                      | in slice 2 | in slice 3 |
| Jobs, notifications, audit             |                      | in slice 2 | in slice 3 |
| Rules and services                     |                      | in slice 2 | in slice 3 |
| Shared schema, models, flag            | slice 1 (foundation) |            |            |

Decision rules:

1. Default to **one slice per concept column**.
2. Ship a horizontal row on its own only when two or more concepts share it (a **foundation** slice), or when a single column is over budget (then split that column into two cells, lower layers first).
3. Never ship a row that nothing uses yet, except a foundation slice used by the slice directly above it.
4. If the feature needs a **keystone** (an entry point to wire, or a flag to activate), it is its own slice, it is last, and it contains nothing but the wiring or activation. Not every feature needs one; say so in the plan when it does not.
5. Refactors that prepare the ground go in their own slice **below** everything else, with no behaviour change.

**Signs you sliced horizontally by accident:** the description says what kind of code it contains ("adds the models and migrations") rather than what the product now does; the tests only prove code exists, not that a behaviour works; or you find yourself writing "will be used later".

## 5. Order the slices

Bottom to top:

1. **Preparatory refactors**, if any (no behaviour change).
2. **Anything another ticket is waiting on.** If a ticket is blocked by part of this work, put exactly that part at the bottom so it can be reviewed and merged first. The blocked ticket's author works on the parts that do not depend on it in the meantime, then continues from `main` once it merges.
3. **Foundation slices.**
4. **Concept slices**, each complete for its concept.
5. **Keystone**, if there is one.

## 6. Write the plan

Write one line per slice saying what the product does after it merges, then check each against section 3 and section 2. Use this format:

```markdown
### Stack plan

Ticket: KEY-123 (acceptance criteria referenced in each slice where they apply)
Landing mode: land as approved
Keystone: slice 4 activates `MeetingEmailsFeature`

| #   | Slice                        | Kind       | After it merges, the product…                       |
| --- | ---------------------------- | ---------- | --------------------------------------------------- |
| 1   | Meeting email foundation     | foundation | does nothing new; the flag exists and is inactive   |
| 2   | Pre-meeting reminder email   | concept    | can send reminders, but no customer can reach them  |
| 3   | Post-meeting follow-up email | concept    | can send follow-ups, but no customer can reach them |
| 4   | Turn on meeting emails       | keystone   | sends meeting emails to customers                   |
```

- **Where it goes:** in the **bottom** pull request's description, where every reviewer and the stack map start. Optionally copy it to the Jira ticket as well.
- **Senior review (heavily recommended):** before coding starts, ask Kevin Ullyott or Dan Harrin to look over the plan. As an agent, remind the user to do this; do not block on it.
- **Landing mode:** _land as approved_ is the default: each slice merges as soon as it is approved. Choose _hold and land together_ only when an intermediate state would be unsafe on `main` even though customers cannot reach it, or when product is still deciding; state the reason in the plan. Mechanics are in `building-and-landing-stacks`.

See [reference/examples.md](reference/examples.md) for candidate slices with verdicts and a complete worked plan.

## Do / Don't

- **Do** keep one pull request when the work fits the budget and is one idea.
- **Do** stop and re-plan as soon as work in progress outgrows the budget.
- **Do** include a use of every new class or method in the slice that adds it.
- **Don't** split by file type or layer just to make pull requests smaller.
- **Don't** let a slice reveal anything unfinished to customers.
- **Don't** mix a refactor or mechanical change with behaviour changes.
